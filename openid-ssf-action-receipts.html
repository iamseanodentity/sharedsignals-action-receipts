OpenID SSF Action Receipts Extension 1.0

Abstract

This document defines an extension to the OpenID Shared Signals Framework (SSF) Specification 1.0 [SSF] that introduces a mechanism for SSF Receivers to send Action Receipts back to SSF Transmitters. An Action Receipt is a Security Event Token (SET) [RFC8417] sent by a Receiver to a Transmitter to indicate that one or more actions were taken in response to a previously received event. Action Receipts reference the originating event via its txn claim and carry freeform human-readable descriptions of the actions taken. This extension defines a new event type, a new Transmitter Configuration Metadata field for advertising the receipt endpoint, and an optional acknowledgement mechanism by which Transmitters may confirm receipt of an Action Receipt.

1. Introduction

The OpenID Shared Signals Framework [SSF] defines a unidirectional flow of Security Event Tokens (SETs) from a Transmitter to one or more Receivers. While this model is well suited to event notification, it provides no native mechanism for a Receiver to communicate back to the Transmitter about actions it has taken in response to received events.

In many deployments, Transmitters benefit from knowing whether and how a Receiver has acted upon a signaled event — for example, whether a session was terminated, a user was prompted for re-authentication, or an access policy was enforced. This feedback enables Transmitters to make better downstream decisions, close audit loops, and satisfy compliance requirements.

This specification defines an Action Receipt mechanism for SSF. An Action Receipt is a SET originated by the Receiver and delivered to the Transmitter via a dedicated endpoint. It references the originating event by its txn claim, describes one or more actions taken by the Receiver in freeform text, and optionally includes structured metadata about each action. The Transmitter MAY optionally acknowledge receipt of an Action Receipt by sending its own acknowledgement SET back to the Receiver via the existing SSF event stream.

1.1. Notational Conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

1.2. Terminology

This specification uses the following terms, in addition to those defined in [SSF]:

Action Receipt
A Security Event Token (SET) originated by an SSF Receiver and delivered to an SSF Transmitter to indicate that one or more actions were taken in response to a previously received SSF event.
Action Receipt Endpoint
An HTTP endpoint hosted by the SSF Transmitter at which it accepts Action Receipts from Receivers.
Receipt Sender
The SSF Receiver that constructs and delivers an Action Receipt to a Transmitter. In the context of an Action Receipt SET, the Receipt Sender acts as the issuer of that SET.
Receipt Acknowledgement
An optional SET originated by the SSF Transmitter and delivered to the Receiver via the existing event stream to confirm that a specific Action Receipt was received and processed.
Originating Event
The SSF event, previously transmitted by the Transmitter, to which an Action Receipt refers.

2. Overview

The Action Receipt flow proceeds as follows:

  1. An SSF Transmitter sends a SET to an SSF Receiver over an established event stream. The SET carries a txn claim that uniquely identifies the underlying event.
  2. The Receiver processes the event and takes one or more actions in response.
  3. The Receiver constructs an Action Receipt SET referencing the originating event's txn value and including a description of the action(s) taken.
  4. The Receiver delivers the Action Receipt SET via an HTTP POST to the Transmitter's Action Receipt Endpoint, which is discovered from the Transmitter Configuration Metadata.
  5. Optionally, the Transmitter MAY send a Receipt Acknowledgement SET back to the Receiver over the existing event stream to confirm processing of the Action Receipt.

The Action Receipt does not alter the semantics of the original SSF event stream. It is a separate, complementary channel from Receiver to Transmitter. Receivers are not required to send Action Receipts, and Transmitters are not required to act upon them beyond acknowledging receipt if they choose to do so.

3. Action Receipt Event Type

3.1. Event Type URI

The Action Receipt event type is identified by the following URI: 

https://schemas.openid.net/secevent/ssf/event-type/action-receipt

Figure 1: Action Receipt Event Type URI

3.2. Event Subject

An Action Receipt SET MUST include a top-level sub_id claim as defined in Section 3 of [SSF]. The subject of an Action Receipt is the same Subject Principal as identified in the Originating Event. The Receipt Sender MUST use the same Subject Identifier format and value as was used in the sub_id claim of the Originating Event, if that information is available to it.

If the Receipt Sender does not have access to the subject of the Originating Event, it MAY omit the specific subject identifier members and instead use an opaque identifier that allows the Transmitter to correlate the receipt to the original event via the ref_txn claim.

3.3. Event-Specific Claims

The event object for the Action Receipt event type, nested within the events claim of the SET, MUST include the claims defined in this section.

3.3.1. The ref_txn Claim

ref_txn
REQUIRED. A string containing the value of the txn claim from the Originating Event SET. This value MUST match exactly the txn value of the event to which this receipt refers. Transmitters MUST use the ref_txn value to correlate an Action Receipt to an Originating Event. If the Transmitter cannot find a previously transmitted event with a matching txn value, it SHOULD log the discrepancy and MAY reject the receipt with an HTTP 422 Unprocessable Content response.

3.3.2. The actions Claim

actions
REQUIRED. A non-empty JSON array of one or more Action Objects (defined in Section 3.3.3) describing the actions taken by the Receiver in response to the Originating Event. A Receipt Sender MAY include multiple Action Objects within a single Action Receipt SET to represent multiple distinct actions taken in response to the same Originating Event. The order of elements in the actions array is not significant.

3.3.3. The Action Object

Each element of the actions array is a JSON object containing the following members:

description
REQUIRED. A string containing a human-readable, freeform description of the action taken by the Receiver. This value MUST NOT be empty. This specification imposes no constraints on the format, language, or length of the description beyond those imposed by JSON string encoding, though Receipt Senders SHOULD keep descriptions concise. Transmitters MUST NOT use this field for automated decision-making without additional out-of-band agreement on a structured vocabulary.
action_time
OPTIONAL. A JSON numeric value representing the time at which the action was taken, as a Unix timestamp (seconds since the Unix epoch), consistent with the definition in [RFC7519]. If omitted, the time of the action is considered unknown.
action_id
OPTIONAL. A string containing a Receipt Sender-assigned identifier for this specific action instance. This value MAY be used by the Transmitter to reference a specific action within an acknowledgement or for logging purposes. The value MUST be unique within the scope of the containing Action Receipt SET.

Action Objects MAY include additional members. Transmitters MUST ignore any members they do not recognize.

3.4. SET Profile for Action Receipts

Action Receipt SETs MUST conform to the SSF SET profile defined in Section 4.1 of [SSF], with the following additional requirements and clarifications:

  • The iss claim MUST identify the Receipt Sender (i.e. the SSF Receiver that is originating the Action Receipt). This value MUST match an identity known to the Transmitter as an authorized Receipt Sender for the stream in question.
  • The aud claim MUST identify the SSF Transmitter as the intended audience of the Action Receipt SET.
  • The iat claim MUST be present and reflect the time at which the Action Receipt SET was issued by the Receipt Sender.
  • The jti claim MUST be present and MUST contain a value that is unique for the Receipt Sender, to enable deduplication by the Transmitter.
  • The txn claim of the Action Receipt SET itself is OPTIONAL. It MUST NOT be confused with the ref_txn field inside the event object, which references the Originating Event.
  • The exp claim MUST NOT be present, consistent with Section 4.1.7 of [SSF].
  • The sub claim MUST NOT be present, consistent with Section 4.1.2 of [SSF].
  • The events claim MUST contain exactly one event, keyed by the Action Receipt event type URI defined in Section 3.1.

4. Action Receipt Endpoint

4.1. Endpoint Advertisement

SSF Transmitters that support this extension MUST advertise the Action Receipt Endpoint by including the following field in their Transmitter Configuration Metadata, as defined in Section 7.1 of [SSF]:

action_receipt_endpoint
OPTIONAL. A URL string identifying the Action Receipt Endpoint at which the Transmitter accepts Action Receipt SETs from Receivers. The URL MUST use the https scheme. If this field is absent from the Transmitter Configuration Metadata, the Transmitter does not support this extension and Receivers MUST NOT attempt to deliver Action Receipts to that Transmitter.

The presence of this field in the Transmitter Configuration Metadata constitutes the Transmitter's declaration of support for this extension. No additional capability negotiation is required to enable the delivery of Action Receipts.

4.2. Request

A Receipt Sender delivers an Action Receipt SET to the Transmitter by sending an HTTP POST request to the action_receipt_endpoint URL. The request MUST conform to the following requirements:

  • The HTTP method MUST be POST.
  • The Content-Type header MUST be application/secevent+jwt.
  • The request body MUST contain a single Action Receipt SET, serialized as a compact JWS [RFC7515].
  • The request MUST be authenticated. The Transmitter MUST define and document the authentication scheme(s) it accepts. Implementations SHOULD use OAuth 2.0 Bearer Tokens [RFC6750] or an equivalent credential issued by the Transmitter to the Receiver out-of-band.
  • The request MUST be made over TLS [RFC8446].

4.3. Response

The Transmitter MUST respond to a valid Action Receipt request with one of the following HTTP status codes:

Status CodeMeaning
202 Accepted The Action Receipt SET was accepted for processing. The Transmitter MAY process the receipt asynchronously.
400 Bad Request The request was malformed (e.g. invalid JWT, missing required claims). The response body SHOULD include an error description.
401 Unauthorized The request was not authenticated or authentication failed.
403 Forbidden The authenticated Receipt Sender is not authorized to submit Action Receipts for the referenced stream or subject.
422 Unprocessable Content The SET was well-formed but semantically invalid — for example, the ref_txn value does not correspond to any known Originating Event.
429 Too Many Requests The Receipt Sender has exceeded the Transmitter's rate limits. The Transmitter SHOULD include a Retry-After header.

The response body for a 202 Accepted response MAY be empty. The Transmitter MUST NOT include any sensitive information about the Originating Event in error responses.

5. Optional Acknowledgement

5.1. Acknowledgement Event Type

A Transmitter that wishes to confirm to a Receiver that an Action Receipt was received and processed MAY send a Receipt Acknowledgement SET. The Receipt Acknowledgement event type is identified by the following URI: 

https://schemas.openid.net/secevent/ssf/event-type/action-receipt-acknowledgement

Figure 2: Action Receipt Acknowledgement Event Type URI

The event object for this event type contains the following claims:

receipt_jti
REQUIRED. A string containing the value of the jti claim from the Action Receipt SET being acknowledged. This allows the Receiver to unambiguously correlate the acknowledgement to a specific previously sent Action Receipt.
status
REQUIRED. A string indicating the outcome of the Transmitter's processing of the Action Receipt. This specification defines the following values:
  • processed — The Action Receipt was successfully processed and the described actions have been recorded by the Transmitter.
  • rejected — The Action Receipt was received but was rejected by the Transmitter. A reason claim SHOULD be included.
  • unknown_event — The ref_txn value in the Action Receipt did not correspond to any Originating Event known to the Transmitter.
Transmitters MAY define additional status values. Receivers MUST treat any unrecognized status value as an opaque string and MUST NOT fail on receipt of an unrecognized value.
reason
OPTIONAL. A human-readable string providing additional context for the acknowledgement, particularly when status is rejected or unknown_event.

5.2. Acknowledgement Delivery

A Receipt Acknowledgement SET is delivered by the Transmitter to the Receiver over the existing SSF event stream using the delivery mechanism already negotiated for that stream (push or poll), as defined in Section 6 of [SSF]. No new delivery endpoint is required.

Receipt Acknowledgement SETs MUST conform to the full SSF SET profile defined in Section 4.1 of [SSF]. The iss claim MUST identify the Transmitter. The aud claim MUST identify the Receiver. The sub_id claim SHOULD use the same Subject Identifier as the Originating Event to which the acknowledged receipt referred, if that information is available to the Transmitter.

Receivers MUST NOT require a Receipt Acknowledgement as a condition of continued event stream operation. The acknowledgement mechanism is strictly OPTIONAL for Transmitters, and its absence MUST NOT be interpreted by the Receiver as an error condition.

7. Security Considerations

7.1. Authorization of Receipt Senders

Transmitters MUST authenticate all requests to the Action Receipt Endpoint and MUST verify that the authenticated identity corresponds to a Receiver that is authorized for the relevant event stream. Transmitters MUST reject Action Receipt SETs whose iss claim does not match the authenticated identity of the requester.

Transmitters SHOULD enforce that an Action Receipt can only reference events that were transmitted on streams to which the authenticated Receipt Sender is subscribed. Accepting receipts referencing events on streams the sender was not party to could enable information inference attacks.

7.2. Replay and Duplication

Transmitters MUST track the jti values of received Action Receipt SETs and MUST reject any SET whose jti has been previously processed. The window over which jti values are retained is at the Transmitter's discretion but SHOULD be sufficient to prevent plausible replay attacks given expected network latency and clock skew. Transmitters SHOULD also validate that the iat claim of an incoming Action Receipt SET falls within an acceptable window of the current time.

7.3. Receipt Forgery

Action Receipt SETs MUST be signed by the Receipt Sender using a key that the Transmitter can verify. Transmitters MUST validate the JWS signature of each incoming Action Receipt SET before processing its contents. Transmitters SHOULD publish the mechanism by which they discover a Receipt Sender's public signing keys (e.g. a JWKS URI endpoint exposed by the Receiver, analogous to the jwks_uri in Transmitter Configuration Metadata).

7.4. Event Enumeration via Receipts

Transmitters SHOULD take care not to reveal, through error responses or acknowledgement messages, information about events that the Receipt Sender was not authorized to receive. In particular, error responses for unmatched ref_txn values SHOULD be indistinguishable from responses for well-formed but unrecognized values, to prevent Receipt Senders from probing for the existence of events on other streams.

8. Privacy Considerations

8.1. Action Description Leakage

The freeform description field within Action Objects may contain sensitive information about a user's activity or an organization's security posture. Receipt Senders MUST ensure that Action Receipt SETs are transmitted only over TLS and only to an authenticated, authorized Transmitter endpoint. Receipt Senders SHOULD apply the principle of minimum necessary disclosure when composing action descriptions and MUST NOT include information beyond what is reasonably required for the Transmitter to understand the actions taken.

8.2. Data Minimization

Receipt Senders SHOULD minimize the personal data included in Action Receipt SETs. In particular, Receipt Senders SHOULD NOT include in the description fields any data beyond a characterization of the action taken. Subject identifiers included in the Action Receipt SET SHOULD be limited to what is necessary to allow the Transmitter to correlate the receipt to the Originating Event. Where the ref_txn value alone is sufficient for correlation, Receipt Senders MAY consider whether inclusion of a full subject identifier is necessary.
